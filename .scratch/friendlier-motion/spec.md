# Implement the approved A interaction design

Status: resolved

## Problem Statement

SWCC already has the appearance and workflow the user wants. They want it to feel friendlier without a redesign. Three existing interactions need clearer visual continuity: an activity reference beneath a learning goal does not visually identify its matching activity card, sidebar selection jumps between destinations, and changing the selected development-plan activity replaces an almost-identical form without making the change obvious.

The user approved prototype A, including its existing gentle feedback and the three added interaction treatments: "Okay, A looks good now." The decision is settled. This is a production implementation handoff, not another design exploration.

## Solution

Keep A's current olive palette, typography, two-column goals-and-activities board, annual progress panel, year picker, navigation order, forms, copy, and editing flow. Add restrained, action-led motion:

- Hovering or focusing a goal's activity reference gives the corresponding activity card exactly the same visual treatment as directly hovering that card.
- A single selection background glides among the first four sidebar destinations. The bottom two keep their existing static selection treatment.
- Page content fades/slides during an accepted page change, independently of the sidebar marker.
- Selecting a different development-plan activity slides the outgoing form out and the incoming form in.
- Preserve A's small press response, softer goal corners, focus treatment, dialog settle, quiet saved confirmation, success sprout movement, and limited new-record reveal.

Animations must not introduce an artificial navigation delay, change saving behavior, replace accessible selection indicators, or prevent input. Reduced-motion users get the same state changes and static highlights without movement.

## User Stories

1. As a portfolio user, I want the app to retain its current appearance, so that I do not have to learn a redesigned interface.
2. As a portfolio user, I want the same navigation destinations, order, wording, and year picker, so that familiar actions stay where I expect.
3. As a portfolio user, I want the overview to keep learning goals and activities in their existing columns, so that I can still see the whole year's relationships.
4. As a portfolio user, I want hovering an activity reference beneath a goal to highlight its activity card, so that I immediately see which record the reference opens.
5. As a keyboard user, I want focusing that reference to produce the same correspondence highlight, so that the connection does not depend on a mouse.
6. As a portfolio user, I want direct card hover and reference hover to look identical, so that both affordances communicate the same activity.
7. As a portfolio user, I want only the referenced activity to receive the association highlight, so that unrelated activities do not appear connected.
8. As a portfolio user, I want either reference to a shared activity to highlight its single card, so that I understand that multiple goals can use one record.
9. As a portfolio user, I want identically titled activities to remain distinguishable, so that highlighting never targets the wrong record.
10. As a portfolio user, I want association highlighting to clear when the reference is no longer hovered or focused, so that old connections do not remain emphasized.
11. As a keyboard-and-pointer user, I want pointer hover to take precedence over a focused reference and focus highlighting to return when the pointer leaves, so that the currently explored connection is unambiguous.
12. As a portfolio user, I want supplementary activities to remain visible and unchanged, so that this interaction does not imply that every activity needs a goal.
13. As a portfolio user, I want the sidebar selection background to move between Year overview, Review, Self-assessment, and Development plan, so that I can follow my change of destination.
14. As a portfolio user, I want sidebar icons and labels to stay in place, so that the moving selection marker does not move my click targets.
15. As a portfolio user, I want All years and Backup and restore to retain static selection, so that the marker does not make a long trip across the sidebar gap.
16. As a portfolio user, I want returning from a bottom destination to establish selection directly on the chosen top destination, so that the marker does not slide from a stale location.
17. As a portfolio user, I want page content to transition alongside navigation, so that the selected destination and the displayed page feel connected.
18. As a portfolio user, I want the page change to proceed without waiting for animation completion, so that decorative feedback does not slow work.
19. As a portfolio user, I want the header, year picker, and sidebar to stay stable while page content moves, so that the app's frame remains predictable.
20. As a portfolio user, I want selecting another activity to visibly replace the development-plan form, so that I know I am editing a different record.
21. As a portfolio user, I want both activity-index selection and goal-reference selection to use that form transition, so that equivalent actions feel consistent.
22. As a portfolio user, I want the activity reference, title, and selected index item to agree with the incoming form, so that I never edit an ambiguous record.
23. As a portfolio user, I want exactly one live editable form during the transition, so that duplicated controls cannot receive input or save the wrong record.
24. As a portfolio user, I want selecting the already selected activity not to replay the animation, so that a redundant click does not disturb my work.
25. As a portfolio user, I want typing, autosaving, validation changes, and evidence updates not to replay the form transition, so that feedback does not compete with editing.
26. As a portfolio user, I want pending edits saved before changing activity or page, so that the transition cannot discard my draft.
27. As a portfolio user, I want save failures and invalid completion dates to keep me on the current editable record, so that motion cannot conceal a blocked action.
28. As a portfolio user, I want the latest eligible selection to win during rapid switching, so that a slower earlier transition cannot restore the wrong activity or page.
29. As a portfolio user, I want returning rapidly to my original record to cancel earlier pending selections without replaying its animation, so that the final visible selection matches my last action.
30. As a portfolio user, I want the quiet Saved confirmation to occur only after a real successful save, so that visual reassurance is trustworthy.
31. As a portfolio user, I want dialogs to settle gently into place while retaining normal keyboard and dismissal behavior, so that they feel approachable without becoming harder to use.
32. As a portfolio user, I want successful explicit confirmation to receive a small, one-shot sprout response, so that completion is acknowledged without confetti or looping motion.
33. As a portfolio user, I want buttons and focused writing fields to respond subtly, so that everyday interactions feel less abrupt.
34. As a portfolio user, I want newly added records to receive only a small local reveal, so that adding one item does not animate the entire page.
35. As a reduced-motion user, I want instant state changes and static correspondence highlights, so that I can use every feature without slides, scales, or rotations.
36. As a reduced-motion user, I want a live preference change to stop movement already in progress, so that I do not need to restart the app.
37. As a small-window user, I want the marker to stay aligned with the responsive navigation buttons, so that selection remains clear when the sidebar becomes a grid.
38. As a keyboard user, I want focus indicators, accessible names, selected/current semantics, tab order, and dialog focus restoration preserved, so that visual motion does not replace accessibility.
39. As an offline user, I want these improvements to work without network requests, new accounts, or external animation services, so that my portfolio remains private and local.
40. As a portfolio user, I want my existing records, evidence, dates, completion state, and backups unaffected, so that a presentation improvement cannot change the meaning or safety of my portfolio.

## Implementation Decisions

1. **Scope and baseline.** Implement A only, including the refinements below. Do not introduce B's expandable goal rows or C's focused-goal layout. Use the current integration/worktree UI as the baseline, not older copy or spacing visible in an archival parent. Preserve existing page headings, prompts, disclaimers, action names, layout density, and empty states.

2. **Existing presentation modules.** Work at the application shell/navigation, overview relationship board, development-plan activity editor, dialog/action feedback, save-status, and shared styling boundaries. Tie motion to meaningful lifecycle changes: an accepted screen change, an accepted activity ID change, a dialog opening, a successful save transition, or an added record. Production must not infer application state from displayed headings or parse references out of accessible names. Prefer normal component state, refs, and existing lifecycle helpers to the prototype's broad DOM observers and imperatively inserted marker. A small shared motion coordinator is appropriate only to centralize cancellation and reduced-motion rules that would otherwise be duplicated.

3. **No data or service changes.** No schema migration, new persistent preference, IPC operation, new backend contract, workflow rule, or regulatory assertion is required. Keep existing draft/review sessions, operation results, save retries, validation, year selection, activity-goal links, evidence ownership, completion logic, and export/backup behavior. Animation cannot mutate records, create extra saves, or mark a step complete.

4. **Fixed visual tokens.** Retain accent olive `#526332`, text `#303b25`, muted text `#647151`, leaf `#dfe8ca`, canvas `#f2f4eb`, and white surfaces `#ffffff`. Retain the existing Trebuchet MS / Segoe UI / sans-serif font stack, type scale, and alignment. Goal cards use a uniform 12 px corner radius instead of 8 px; this is not a new radius applied to every component. Preserve other component radii, spacing, and selected/unselected activity-index corner consistency.

5. **Linked activity highlight.** Resolve a goal reference to the activity by stable activity identity, not title, DOM position, or a substring of its reference. Direct card hover, direct card keyboard focus, and linked-reference hover/focus share one treatment: canvas background `#f2f4eb`, olive border `#526332`, an inset 1 px olive outline, and the existing brightness treatment of `0.94`. Do not grow, lift, scroll to, select, open, or write the activity on hover/focus. Keep the card's dimensions unchanged. Only the corresponding card receives the association highlight. A shared activity has one card, irrespective of how many goals reference it. Pointer hover of a reference takes precedence over reference focus; on pointer exit, restore a still-focused reference's association. Clear stale association state on blur, leaving the board, changing year, or leaving the overview. Normal direct card hover/focus remains independent and accessible.

6. **Sidebar selection marker.** Move the existing translucent selection background behind the first four complete button tiles; do not slide or morph their icon glyphs, move their labels, or change their hit targets. The target order is Year overview, Review, Self-assessment, Development plan. Move the background's position over 240 ms with `cubic-bezier(.2,.8,.2,1)`; its width and height settle over 240 ms with `ease` if button sizes differ. Keep the established translucent white background (`#ffffff24`) and 8 px marker radius. The marker is decorative, hidden from accessibility, non-interactive, and behind button content. Keep the actual button's current-page semantics. All years and Backup and restore retain their original static selected backgrounds and receive no traveling marker. Hide the top-four marker immediately on either bottom destination; returning to a top destination snaps to its correct location rather than gliding from its previous top destination. Initial placement is also a snap. Recalculate position and dimensions from actual navigation geometry; viewport/layout changes snap into alignment rather than animating across the old and new layouts. Do not change sidebar ordering, bottom-item anchoring, sticky behavior, overflow, or keyboard visibility.

7. **Page transition.** Animate main page content only; the shell/header/year picker remain fixed and the sidebar marker moves separately. On an accepted change, outgoing content fades from opacity 1 to 0 and moves from 0 to -12 px horizontally over 180 ms with `ease`. Incoming content moves from +12 px to 0 and fades from 0 to 1 over 240 ms with `cubic-bezier(.2,.8,.2,1)`. If snapshot geometry needs to settle, use a 260 ms scope duration. Do not add a timeout before accepting a destination and do not wait for the marker or page animation to finish before committing the accepted screen. Existing required save/validation/operation waits remain. Clicking the current destination does not replay an entrance; it must still supersede an earlier eligible pending transition when necessary. Do not animate the whole card grid on startup or re-run a page entrance on typing, saving, readiness updates, or routine rendering.

8. **Activity-form transition.** Apply this when the development plan accepts a different selected activity, through either the activity index or a goal's activity reference. Keep the activity index, goal-connection strip, plan date, and readiness panel stable; animate only the editor. Outgoing editor content fades from opacity 1 to 0 and moves from 0 to -24 px horizontally over 180 ms with `ease`. Incoming editor content moves from +24 px to 0 and fades from 0 to 1 over 260 ms with `cubic-bezier(.2,.8,.2,1)`. Coordinate the selected index/ref state and incoming title/reference with the committed activity. Selecting the current activity, editing its fields, autosave, readiness changes, evidence refresh, or a normal rerender does not replay the swap. Preserve creation/deletion behavior and field layout, including the completion-date picker appearing only when appropriate. Selecting an existing Completed record must not spuriously open or focus its date picker. A local added-record reveal is separate from changing an existing selection.

9. **Commit ordering, cancellation, and interaction safety.** Start page/activity motion at the existing accepted-change boundary, after the existing draft/review flush has succeeded. On failed save or invalid activity input, keep the current screen/editor and retained text; display the existing recovery/validation feedback and do not begin a destination transition. Do not weaken existing busy/disabled gates. Once an action is eligible, animation completion is never a prerequisite for the next action. Every eligible selection intent participates in cancellation/order tracking, including an intent that returns to the currently visible record/page. The latest eligible intent must win; skip stale pending visual work and prevent its later callback from committing an obsolete selection. The same-selection fast path must not bypass that cancellation. Cancel obsolete animations and clean up their resources on new selection, unmount, preference change, and disabled motion. Preserve exactly one live editor and one set of its interactive controls. Keep keyboard focus and input associated with the live UI, not outgoing imagery.

10. **Snapshot implementation and fallback.** The approved prototype uses the browser's native view-transition snapshots for outgoing/incoming page or editor content. Feature-detect support in the shipped Electron renderer; do not assume the development browser proves production support. Keep page and activity transition scopes distinct so a local form swap does not capture or animate the entire page. Transition imagery must not intercept pointer input, trap focus, clone live forms, duplicate IDs, or trigger record lifecycle work twice. Handle the expected readiness `AbortError` from intentionally skipped transitions; do not blanket-catch other rendering, save, or operation errors. If native snapshots are unavailable, commit normally and provide an incoming-only animation: page opacity `0.35` and horizontal offset +12 px to opacity 1 and offset 0 over 220 ms; editor opacity `0.15` and offset +24 px to opacity 1 and offset 0 over 260 ms. Use `cubic-bezier(.2,.8,.2,1)` for these fallbacks. Do not delay the real change or fabricate an outgoing editable copy to emulate unsupported snapshots.

11. **Preserve A's existing micro-feedback.** Implement the following together with the three main additions; do not use them as reasons to redesign surrounding UI.

    | Interaction | Approved treatment |
    | --- | --- |
    | Ordinary button press | Scale to `0.98` only while pressed; restore on release. Transform transition: 100 ms `ease`. Keep text-button and tab affordances from receiving this generic scale. |
    | Sidebar button press | Small press scale `0.96`; selection travel is the separate marker treatment. This press feedback does not make the bottom two options participate in marker travel. |
    | Button color/border feedback | Background and border transitions: 140 ms `ease`. No card-hover lift or translation. |
    | Focused writing field | Background `#fbfcf8`, border `#526332`; border/background settle over 160 ms `ease`. Retain the existing visible focus outline and typing/caret behavior. |
    | Save-status presentation | Quiet canvas pill, 20 px radius, 6 px vertical / 9 px horizontal padding, 6 px icon/text gap, minimum 80 px width. A small check accompanies the actual Saved state; status/error wording and accessible status remain truthful. |
    | Successful autosave response | Only on actual Saving -> Saved: scale `0.97` / background `#dfe8ca` to scale 1 / background `#f2f4eb` over 360 ms with `cubic-bezier(.2,.8,.2,1)`. No pulse on initial load, every keystroke, a failed save, or unrelated rendering. |
    | Dialog opening | Opacity `0.45`, vertical offset +8 px, scale `0.985` to opacity 1, offset 0, scale 1 over 220 ms with `cubic-bezier(.2,.8,.2,1)`. No delayed dismissal. Preserve modality, scrollable content, Escape/backdrop behavior, focus trapping/restoration, and action names. |
    | Explicit success confirmation | One small existing sprout movement: -7 degrees, +3 degrees, then 0 degrees over 420 ms with `cubic-bezier(.2,.8,.2,1)`. Only genuine explicit success feedback triggers it, not error/information feedback or each autosave. No new mascot or looping behavior. |
    | Local new-record reveal | Where A reveals a genuinely added item in an already visible list: opacity `0.4` / scale `0.99` to opacity 1 / scale 1 over 220 ms with `cubic-bezier(.2,.8,.2,1)`. Do not stagger every existing card, replay on page/year entry, or animate ordinary edits. |

12. **Reduced motion and offline operation.** Respect the OS/browser reduced-motion preference from the first render and react to live changes. Disable slides, scaling, rotations, position interpolation, and transitional entrances; place the marker and display the final page/editor immediately. Stop in-flight movement when the preference changes. Keep all static highlights, focus indicators, selected/current semantics, status messages, and real state changes. Honor the prototype's manual motion-off control in the archive and any existing motion-disable mechanism in the production environment, but do not add a new production settings screen or persist a preference for this task. No new animation dependency, external font, network request, image service, or remote asset is necessary.

## Testing Decisions

- **One highest-level seam:** the existing production Electron desktop UI exercised through Playwright. Reuse the temporary per-test user-data directory, offline launch, accessible role/label interactions, and existing failure fixtures. Do not add a parallel browser-only fake application as the production acceptance seam or require a new test abstraction across modules.
- **Good tests observe user-visible behavior:** correspondence, selected destination, displayed editor/reference/title, geometry during/after movement, focus, input retention, accessible semantics, real save outcomes, and settled final state. Do not merely assert animation class names, CSS constants, a component's private state, helper call counts, or the prototype's observer implementation. Use frame-aware polling for movement/readiness/settling; avoid exact elapsed-time assertions or sleeps that assume snapshots start in the same frame as the React commit.
- **Prior art:** extend the existing desktop activity and overview-action suites for linked records, editor selection, card geometry, and small viewports; the draft-recovery suite for flush-before-navigation and persistence under failed writes; and the feedback suite for modal accessibility and focus restoration. The concrete starting points are `tests/desktop/activities.spec.ts`, `tests/desktop/assessment-action.spec.ts`, `tests/desktop/drafts.spec.ts`, and `tests/desktop/feedback.spec.ts`. Existing unsupported-date-picker checks demonstrate feature-detection/fallback testing without creating a new public seam.
- **Correspondence fixture:** include several goals, an activity shared by two goals, another linked activity, and an unlinked supplementary activity. Include two different activities with the same title. Pointer hover and keyboard focus of each reference must identify its actual record, direct card hover must match the association style, and association must clear/restore appropriately. Clicking still opens the same single record.
- **Navigation acceptance:** exercise all four moving destinations; verify the marker visibly moves, settles on the actual selected tile, and does not move the icons/hit targets. Exercise both bottom destinations and return to a top destination; verify static bottom selection, no gap traversal, and direct top placement on return. Check current-page semantics and keyboard activation. Repeat relevant geometry checks after resizing to a small navigation-grid viewport.
- **Page acceptance:** verify the destination's real UI is committed without waiting for visual completion, the frame remains stationary, and outgoing/incoming content moves and settles. Same-page clicks and ordinary edits/readiness updates must not replay entrances. An animation overlay must not block a subsequent eligible action.
- **Form acceptance:** select another activity from the index and from a goal reference; observe movement and the correct final title/reference/selected index item, with only one live editor. Check that the index and plan/readiness surroundings do not slide. Re-select the same record and edit/autosave it; no swap replay. Preserve evidence, reflections, linked goals, and completed-date behavior.
- **Data safety acceptance:** edit an activity and immediately select another; return and verify the edit persisted in the original record. Exercise real failed-save and invalid/missing Completed-date cases with the existing fixture patterns: selection/navigation remains on the retained current record and no destination animation runs. Existing retry, close-flush, and offline restart behavior must remain correct.
- **Cancellation acceptance:** rapidly choose distinct activities and finish on the original visible activity, then verify the settled final selection after all earlier work could have completed. Repeat with a different final record. Exercise a subsequent normal selection to ensure cancellation did not disable later motion. Check rapid eligible page changes and preference changes during movement. Expected skips produce no unhandled promise rejection; genuine failures remain explicit.
- **Motion preference/fallback acceptance:** run the relevant interaction checks with reduced motion, including changing the preference while a transition is active. State changes and static association still work, the marker remains correctly positioned, and no movement continues. Feature-disable native view transitions in a controlled test and verify immediate commits plus the incoming-only fallback. The archived prototype's manual motion-off must also disable native and fallback movement.
- **Visual acceptance and required checks:** review desktop and small-window screenshots against approved A, including hover and form/page switching; ensure no horizontal overflow, detached marker, clipped focus/controls, or unexpected layout/copy change. Run the existing typecheck, lint, build, and the smallest combined relevant desktop test selection. Broaden only for a demonstrated regression. Acceptance must include the production build/runtime, not just the Vite preview.

## Out of Scope

- Another design exploration, B/C layouts, new palettes/fonts, a mascot, confetti, looping animation, hover lifts, or initial staggered page/card entrances.
- Changing navigation order, sidebar spacing/anchoring, headings, prompts, form structure, action names, annual workflow, completion rules, dates, evidence relationships, backup/export behavior, or regulatory disclaimers.
- Delaying business state commits until animation completion, bypassing save/validation/busy gates, discarding drafts, or introducing optimistic success-shaped status.
- Schema/IPC changes, persistent motion settings, a new settings screen, new libraries, remote assets, or a new testing platform.
- Shipping the throwaway routes, variant switcher, comparison controls, state/debug panel, sample data, disconnected operation adapter, development-only entrypoint, or prototype-specific props/DOM instrumentation as the production architecture.
- Fixing unrelated pre-existing worktree issues or merging/reverting another contributor's pending edits.
